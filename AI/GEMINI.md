# 프로젝트 작업 규칙 및 추적 가이드 (Global Rule)

본 가이드는 에이전트 작업의 연속성을 확보하고, 모든 산출물(Artifact)을 자산화하며, 세션 간 작업 맥락을 최대한 정확하게 복구하기 위한 최상위 지침입니다.

---

참고

- **YYYY_MM_DD:** 오늘 한국시 날짜

---

## 0. 세션 시작 체크 (Session Start Protocol)

새로운 세션 시작 시, 에이전트는 작업을 시작하기 전 아래 절차를 수행하고 사용자에게 **3~5문장 이내로 요약 보고**합니다.

1. **로그 확인 (우선순위)**
   - 1순위: 현재 `branch` 또는 작업 `topic`과 일치하는 가장 최근 로그 확인
   - 2순위: 일치하는 파일이 없으면 `work_log/*.md` 중 최신 로그 확인
2. **Git 상태 및 히스토리 점검**
   - 현재 `branch`, `status` 확인
   - 최근 커밋 3~5개 또는 현재 마일스톤과 직접 관련된 커밋을 우선 확인하여 작업 흐름 파악
3. **Task 및 Blocker 식별**
   - 진행 중이던 마일스톤 확인
   - 미완료 Task 확인
   - 해결되지 않은 Blocker 확인
4. **충돌 방지**
   - 현재 작업 예정 파일에 미반영 변경, 충돌 가능성, 미정리 상태가 있는지 확인
5. **사용자 보고**
   - 현재 상태, 이어서 할 작업, 주요 Blocker를 짧게 요약하여 보고 후 시작

## 1. 작업 단위 및 커밋 규칙

- **마일스톤 기반 작업:** 모든 작업은 '마일스톤' 단위로 정의하고 진행합니다. Task 아티팩트(Task List) 생성 시, 전체 작업을 논리적 단위(예: 페이지 섹션, 핵심 기능 등)로 잘게 쪼개어 각각을 마일스톤으로 세분화해야 합니다.
- **Task 저장 및 커밋 동기화:** 작업 시작 전 최종 Task List는 반드시 `work_log/{YYYY_MM_DD}_{branch_or_topic}_task.md` 경로의 파일로 저장합니다. 마일스톤 단위 작업이 끝나면 사용자 확인 및 필요한 수정 반영을 완료한 뒤, 커밋 직전에 시스템 내장 Artifact의 Task와 `work_log/..._task.md` 파일을 최종 상태로 동일하게 업데이트합니다.
- **Task와 커밋의 일치 (원칙: 1 Milestone = 1 Commit):** Task 리스트 작성 시 각 마일스톤 제목 하단에 해당 마일스톤 완료 시 사용할 **커밋 메시지를 미리 명시**합니다. (예: `> chore(init): setup project`)
- 기본적으로 각 마일스톤은 하나의 커밋 단위로 설계합니다.
- 다만 마일스톤 규모가 큰 경우에는 sub-milestone 단위로 분할 커밋할 수 있으며, 이 경우에도 각 커밋이 Task 상의 논리적 완료 단위와 대응되도록 유지합니다.
- **커밋 시에는 코드 변경사항뿐만 아니라 업데이트된 `_task.md` 파일과 메인 작업 로그(`work_log/... .md`) 파일이 반드시 포함되어야 합니다.**
- **커밋 전 사용자 확인 (강제):** 마일스톤 작업 완료 후, 에이전트는 사용자에게 추가 수정사항 또는 변경 요청 여부를 반드시 확인해야 하며, **사용자의 명시적 승인 또는 "추가 수정 없음" 확인 전에는 절대로 커밋할 수 없습니다.**
- **커밋 전 확인 질문 고정:** 마일스톤 또는 추가 수정사항 완료 후 커밋 전에 반드시 아래와 같은 취지로 사용자에게 질문합니다.
  - `현재 마일스톤(또는 수정사항) 작업이 완료되었습니다. 커밋 전에 추가 수정사항이나 변경 요청이 있으신가요?`
- **미커밋 완료 마일스톤 잠금:** 완료되었으나 아직 커밋되지 않은 마일스톤이 존재하는 경우, 에이전트는 다음 마일스톤의 구현, 수정, 분석, 추가 작업을 시작할 수 없습니다. 먼저 사용자 확인 → 필요한 수정 반영 → Task/로그 업데이트 → 커밋 순서를 완료해야 합니다.
- **커밋 기준:** 최소 하나의 논리적 변경 단위(마일스톤)가 끝날 때 수행하며, 큰 마일스톤은 중간 단위(sub-milestone) 커밋을 허용합니다.
- **커밋 메시지 규격:** `type(scope): summary` 형식을 사용합니다. (예: `feat(auth): add refresh token validation`)

## 2. 작업 상태 및 아티팩트 기록 (Work Log)

- **파일명 규칙:** `work_log/{YYYY_MM_DD}_{branch_or_topic}.md`
- **기록 방식:** 중요한 전환점마다 상세 기록하되, 모든 로그는 파일 끝에 **Append(추가)** 방식으로 기록합니다.

### [작업 로그 업데이트 템플릿]

#### 🔄 Current Snapshot

- **현재 마일스톤:** (진행 중인 목표)
- **현재 상태 / 요약 Task List:** (전체 현황을 한눈에 볼 수 있게 요약)
- **마지막으로 완료한 작업:**
- **현재 막힌 이슈 (Blockers):**
- **다음 바로 할 일:**
- **영향 범위 / 리스크:** (이번 변경이 미치는 범위와 잠재 리스크)

#### 📋 1. Task List & Implementation Plan

- **상태 변경 Task:** (전체를 반복하지 않고, **이번 업데이트에서 상태가 변한 항목** 중심으로 기록)
- **구현 계획:** (기술적 접근 및 주요 변경 로직 요약)

#### ✅ 2. Validation / Verification

- **실행 명령어 및 결과:** (예: `npm run test` -> 성공 / 미검증 시 사유 명시)
- **수동 검증 항목:** (예: UI 실제 동작 확인 등)
- 검증 결과가 실패인 경우에도 숨기지 않고 실패 원인과 현재 상태를 함께 기록합니다.

#### ⚠️ 3. Blockers / Decisions

- **Blocker:** (작업을 막고 있는 이슈)
- **Decision:** (이번 작업에서 내린 **단기적 의사결정**)
- **Reason:** (해당 결정을 내린 근거)

#### 📂 4. Changed Files

- `파일 경로` - (왜 바꿨는지에 대한 짧은 이유 포함)
- _예: `src/auth/AuthService.ts` - refresh token 검증 로직 추가_

#### 🚀 5. Walkthrough & Knowledge

- **단계별 가이드(Walkthrough):** (에이전트가 수행한 작업 순서 설명)
- **지식 자산(Knowledge):** (이후 세션에도 반복 활용될 **장기적 규칙/교훈/주의점**만 기록)

#### 🖼️ 6. Visual Assets & Evidence

- **Screenshots / Recordings:** (파일명/경로 기록, 없으면 "없음" 명시)

#### 📎 7. Generated Artifacts

- `work_log/{YYYY_MM_DD}_{branch_or_topic}_{artifact_name}.md` - 생성 목적 및 다음 단계에서의 사용 용도
  - Task List / Implementation Plan / Walkthrough / Knowledge
- `파일 경로 또는 참조`
  - Screenshots / Browser Recordings

### 아티팩트 별도 문서화 규칙

- 다음 단계 진행의 기준이 되는 최종 산출물(Implementation Plan, Task List 등)은 반드시 별도 Artifact 파일로 저장합니다.
- Artifact 파일명 규칙은 `work_log/{YYYY_MM_DD}_{branch_or_topic}_{artifact_name}.md` 를 사용합니다.
- Artifact를 생성한 경우, 해당 세션의 기본 `work_log/{YYYY_MM_DD}_{branch_or_topic}.md` 파일에도 생성 사실과 파일 경로를 함께 기록합니다.
- 동일 성격의 Artifact를 반복 생성할 경우, 파일명이 중복되지 않도록 의미 있는 `artifact_name`을 사용합니다.

## 3. 완료 기준 (Definition of Done)

작업은 아래 항목을 모두 만족해야 완료로 간주합니다.

1. 요구사항 구현 및 수정 완료.
2. 관련 테스트 또는 수동 검증 완료 및 결과 기록.
3. 빌드/린트/타입체크 통과 확인.
4. 영향 범위 및 리스크 기록.
5. **관련 문서, 설정 파일, 예시 값 반영 여부 확인.**
6. `work_log`에 검증 결과, 변경 파일, 의사결정, 리스크가 반영되었는지 확인합니다.
7. 논리적 변경 단위(마일스톤)가 완료된 경우 해당 변경에 대한 커밋까지 완료합니다. **이때 커밋에는 반드시 업데이트된 Task List(`work_log/*_task.md`)와 메인 작업 로그(`work_log/*.md`) 파일이 포함되어야 합니다.** 단, 코드 변경이 없는 조사/분석 단계는 예외로 할 수 있습니다.
8. 마일스톤 완료 후, 사용자에게 추가 수정사항 또는 변경 요청 여부를 반드시 확인하며, **사용자의 명시적 승인 또는 "추가 수정 없음" 확인 전에는 커밋하지 않습니다.**
9. 완료되었으나 아직 커밋되지 않은 마일스톤이 존재하는 경우, 다음 마일스톤의 구현, 수정, 분석, 추가 작업을 시작하지 않습니다. 먼저 해당 마일스톤의 사용자 확인, 수정 반영, Task/로그 반영 및 커밋을 완료해야 합니다.
10. 다음 단계 진행 기준이 되는 Artifact(예: Task List, Implementation Plan, Walkthrough, Knowledge)가 있는 경우, 해당 내용을 별도 Artifact 파일로 저장하고 기본 `work_log`에도 참조를 남깁니다.
11. Screenshots와 Browser Recordings는 별도 파일 경로 또는 참조 정보만 기록할 수 있습니다.

## 4. 최소 기록 기준 (경미한 수정 시)

작업 내용이 경미하여 상세 기록이 불필요한 경우, 아래 항목만 최소한으로 기록할 수 있습니다.

- `Current Snapshot`, `Validation`, `Changed Files`, `Decision/Reason`

## 5. 검증 및 변경 추적 원칙

- 모든 코드 변경에는 가능한 경우 검증 절차를 수행하고 결과를 기록합니다.
- 검증 불가 항목은 "미검증"으로 명시하고 이유를 남깁니다.
- 막힌 이슈, 보류 사유, 임시 우회책(Workaround)은 반드시 기록합니다.
